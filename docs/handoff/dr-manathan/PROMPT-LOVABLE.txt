PHASE 2 — ORDRES TEXTE ET AUDIO

Créer un routeur déterministe partagé, par exemple src/lib/assistant-commands.ts. L'appeler pour le texte avant enqueueText et pour la transcription dans src/components/voice/voice-session.ts avant runAnswer. Même commande = mêmes permissions, effets et résultat dans les deux modes d'entrée. Ne pas déléguer les bascules d'état à une simple promesse du LLM.

Séparer trois états : microphoneEnabled, speechOutputEnabled, assistantMode. Aujourd'hui mute() coupe le micro seulement et le micro actif impose la réponse vocale. Corriger cette confusion sans casser la file FIFO, la pause sur erreur, l'annulation et la lecture intégrale des questions ordinaires.

Commandes minimales : « mode silence », « réactive la voix », « coupe le micro », « passe en mode DR MANATHAN », « retour à MAVAI », « arrête », « reprends », « répète », « nouvelle conversation », « ouvre mon projet … », « recherche … », « résume … », « exporte … ». Activer uniquement celles dont l'outil existe. Grammaire stricte, accents/casse normalisés, ambiguïté clarifiée. Un mot cité dans un document ou la phrase « écris le mot silence » ne déclenche rien.

Avant dispatch, produire un accusé visible « Oui chef, … » pour mon compte ; audio si la sortie l'autorise. En silence, garder l'accusé texte. Ce reçu signifie « ordre compris », pas « action terminée ». Afficher ensuite le résultat réel. Pour silence/arrêt urgent, l'accusé texte précède immédiatement l'interruption ; ne pas attendre un appel TTS réseau avant de couper le son. Ces contrôles doivent contourner l'attente FIFO, tout en préservant les questions ordinaires déjà en file selon l'intention de l'ordre.

« Silence » coupe la sortie vocale ; le micro peut rester actif si l'écoute a été autorisée, pour recevoir « réactive la voix ». « Micro coupé » désactive la capture ; annoncer alors une reprise par clic ou clavier. Ne jamais promettre un réveil vocal avec le micro désactivé. Ne pas ouvrir le micro automatiquement lors d'un changement de mode.
